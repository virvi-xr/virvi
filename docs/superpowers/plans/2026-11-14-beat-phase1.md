# BEAT Phase 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Hosts pay for a BEAT, visitors who opt in and stay long enough claim it in-world, and Virvi's minter wallet mints it to them on Polygon.

**Architecture:**
- **Contract:** a Foundry project in `contracts/`: `VirviBeat.sol` (ERC-1155, OpenZeppelin 5), its tests, a Slither config and an owner-run deploy script.
- **Server:** a new `apps/server/src/beats/` module with five tables. It covers:
  - host routes and payments, on the studio-payments pattern;
  - visitor routes, using the raffle's attendance helpers;
  - public metadata;
  - a locked 60-second job that sends and reconciles every minter transaction;
  - admin routes.
- **Web:** a dashboard BEATs page, an admin BEATs page, and the contract listed on `/transparency`.
- **In-world:** a BEAT card in `packages/adapter-dcl`, shipped as `@virvixr/dcl` 2.16.0 and runtime v15.

**Tech Stack:** Solidity 0.8.28, Foundry, OpenZeppelin Contracts 5.4.0, Slither, ethers 6, Fastify, drizzle and Postgres, vitest, Next.js static export, Decentraland SDK7 React-ECS.

**Spec:** `docs/superpowers/specs/2026-11-14-beat-phase1-design.md`. Read all of it. **Settled details** at the end overrides the text above it.

## Review Focus

1. **A smart-contract wallet that can't receive ERC-1155** (no `onERC1155Received`) would revert a whole 200-address `mintTo`, and every other claim in that batch would stall. Expected: the job checks each wallet's code, sends contract wallets alone, and a revert fails only that one claim. Tested in Task 7.
2. **A transaction that never confirms** (dropped, or underpriced during a gas spike), or a crash between signing and recording it. Expected:
   - no claim is lost and no nonce is skipped;
   - the same nonce is rebroadcast or re-signed with higher fees;
   - nobody is minted twice, which the contract also guarantees.

   Tested in Task 7.
3. **Two claims racing for the last place under the cap,** or one visitor claiming from two scenes at once. Expected: exactly one succeeds and the other gets `all_claimed`, or the same claim back. Tested in Task 8.
4. **Wallets and marketplaces asking for metadata** with the ERC-1155 `{id}` form: 64 lowercase hex digits, no `0x`. Also unknown, cancelled or draft ids. Expected:
   - both decimal and hex resolve to the same JSON;
   - unknown, cancelled and draft ids return 404;
   - frozen BEATs never change.

   Tested in Task 8.
5. **A visitor who opted in, then deleted their data while their claim was mid-mint.** Expected: the row is kept until the batch settles. Then the account link and name are removed if it minted, or the row is deleted if the batch failed. Tested in Task 9.

- In `_update`, when `from != address(0) && to != address(0)`, it reverts with `NotTradeable(id)` for any id with `tradeable == false`. Mint (`from == 0`) and burn (`to == 0`) always pass.
- Nothing payable: no `receive` or `fallback`.

### Task 7: The minting job

**Files:**
- Create: `apps/server/src/beats/job.ts`
- Modify: the server start-up that calls `startErrorJobs()`. Also call `startBeatJobs()` when `config.beats.enabled`.
- Test: `apps/server/test/beat-job.test.ts`, using `fakeBeatChain`.

**Interfaces:**
- Produces:
  - `runBeatTick(now = new Date()): Promise<{ sent: number; confirmed: number; failed: number; paused: BeatChain[] }>`. It runs once under `withLock('beat-minter', …)` from `apps/server/src/errors/jobs.ts`, and returns null-equivalent zeros when it doesn't win the lock.
  - `startBeatJobs(): () => void`: every `BEAT_JOB_EVERY_MS`.
  - `retryFailedClaims(beatId?: string): Promise<number>`, for the admin button. It sets failed claims back to `claimed` and clears `fail_reason`.
  - `beatPaused(chain): { paused: boolean; reason: 'low_gas' | 'no_client' | null }`. It's kept in memory and set each tick.

**Each tick, for each chain with a client:**
1. **Statuses:**
   - `paid → live` when `starts_at <= now`;
   - `live → ended` when `ends_at <= now`.
2. **Reconcile the open transaction** (at most one per chain is ever open, in status `sending` or `sent`):
   - **A receipt for any of its `tx_hashes`:**
     - if it's ok and has the chain's confirmations: mark the batch `confirmed`; for `mint`, mark its claims `minted` with `mint_tx` and `minted_at`; for `create`, set the BEAT's `created_on_chain_tx` and `created_on_chain_at`;
     - if it's ok but not deep enough: wait;
     - if it reverted: treat it as a failed send (below).
   - **No receipt, and the chain's `latest` nonce is past the batch nonce:** the nonce was used by another of our hashes that we lost, or the tx was replaced. Check `isMinted` for each wallet (or `exists` for create). Mark the minted ones, put the rest back to `claimed`, and mark the batch `failed` with `last_error = 'replaced'`.
   - **No receipt, and the nonce isn't used:**
     - if `status = 'sending'`, broadcast `raw_tx` and set `sent`;
     - if it was sent more than `BEAT_REPRICE_AFTER_MS` ago, re-sign the same nonce with fees raised by `BEAT_FEE_BUMP_PERCENT` (and at least the current fee data), append the hash, broadcast, and update `raw_tx` and `sent_at`.
   - While a transaction is open, nothing new is sent on that chain. **[Ruling: one open tx per chain keeps nonces simple; about 200 mints a minute is enough for phase 1.]**
3. **Gas:** if `balanceWei() < config.beats.minGasWei`, set paused `low_gas` and stop for this chain. Claims wait.
4. **Send the next transaction, in this priority:**
   - **(a)** A `create` for the oldest BEAT in `paid` or `live` with no `created_on_chain_tx` and no open create batch.
   - **(b)** Otherwise, a `mint` for the BEAT with the oldest `claimed` claim. The BEAT must be created on chain. Take up to 200 claims, ordered by `claimed_at`, with `for update skip locked`.
     - Partition the wallets by `codeAt`.
     - If there are any EOAs, mint those together.
     - Otherwise, mint the first contract wallet alone (Review Focus 1).
   - **Steps for (a) or (b):**
     1. `estimate`, then send with gas limit = estimate + `RECEIVER_GAS` for each recipient with code + 10%. A revert with `InsufficientGas` on execution counts as a failed send. The retry splits the batch in half.
     1a. (was 1) A `BeatRevert` from `estimate`: A `BeatRevert` on a single-wallet mint marks that claim `failed` with `fail_reason` set to the error name. On a batch, it falls back to single sends on the next ticks, by marking the batch so its wallets are retried one by one.
     2. Nonce = `max(chain pending nonce, last batch nonce + 1)`.
     3. `sign`, then insert the batch with status `sending`, `raw_tx`, `tx_hashes = [hash]`, the nonce and the wallets. Set the claims to `minting` with `batch_id`. All of this happens in one transaction, before broadcasting.
     4. `broadcast`, then set the batch to `sent` and `sent_at`.
5. **Send failures:**
   - An RPC error or timeout on broadcast leaves the batch `sending`. Step 2 retries it on later ticks.
   - Each failed try increments `attempts` and sets `next_attempt_at = now + 2^attempts minutes`.
   - At `BEAT_SEND_MAX_ATTEMPTS`: for a mint batch, run the same `isMinted` check as step 2; mark the batch `failed`, the claims that aren't minted `failed`, and record a job failure through the existing job-failure recording (look at how `errors/jobs.ts` reports failures, and use the same path) so admins are alerted.
6. **Contract-level skips and closing:**
   - When a confirmed mint receipt has `MintSkipped` logs, those claims become `failed` with `fail_reason = 'receiver_rejected'`. The other claims are minted.
   - A `create` that reverts with `BeatExists` pauses the chain (`reason: 'id_conflict'`, a new value) and records a job failure. Never skip ahead silently.
   - Once a BEAT is `ended`, `ends_at + BEAT_CLAIM_GRACE_MS` has passed and it has no `claimed` or `minting` claims, send `closeBeat` (kind `close`, lowest priority). Record `closed_on_chain_at` (add the column in this task, with the entrypoint SQL).
7. **Freeze:** when a mint batch confirms, set `beats.frozen_at = now` where it's null, in the same transaction.
8. **Settle delete requests:** for claims in a settled batch with `delete_requested`, delete the row if it isn't minted. If it is minted, null `user_id` and `display_name`.
